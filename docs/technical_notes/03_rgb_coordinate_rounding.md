# 技術ノート 03: RGB描画における座標の丸めによる差異

> 後輩が同じ問題に遭遇したときの参考用。入力画像を過去のPilotと「ぴったり一致」させようとして、
> わずかな画素差・ハッシュ不一致に悩むケース。原因は「丸め」と「ハッシュの計算方式」であって、処理の誤りではないことが多い。
> 一次ログは研究室Mac上にあり、本文書更新環境では再照合していない。ここでは現象・原因・対処を整理する。

## 現象

RGB画像とフロアプランを横連結したモデル入力を生成し、**過去のPilotの入力と画像・テンソルを比較**したところ、

1. **RGB画像にわずかな画素差**が出る、
2. **画像ハッシュが一致しない**、

という2つのズレが観測された（報告）。いずれも「描画や前処理を間違えた」のではなく、**計算方式の差**で説明できた。

## 原因の切り分け

### (1) 画素差 ← 開始位置の小数第3位への丸め

- 地図や軌跡の描画は、エージェントの連続座標（float）を画素座標へ変換して行う。
- **開始位置を小数第3位へ丸める**かどうかで、画素座標が1px単位でずれることがあり、その結果 RGB（または連結画像）に
  **わずかな画素差**が生じる。
- 本研究では、観測された画素差が**この丸めに起因する**ことを確認した（報告）。＝描画ロジックの誤りではない。

### (2) ハッシュ不一致 ← int32 キャスト と SHA-256 短縮表示の計算方式差

- 画像・テンソルの同一性確認に使うハッシュが一致しない原因は、**ハッシュの取り方そのものの違い**だった。
  - 一方は **int32 へキャスト**した値に対するハッシュ、
  - もう一方は **SHA-256 を短縮表示**したもの、
  と**計算方式が異なっていた**（報告）。
- つまり「中身が違う」のではなく「**ハッシュの定義が違う**」ために不一致に見えていた。

## 後輩への教訓

- 入力の同一性を確認するときは、**同じ丸め規約・同じハッシュ定義**で比較する。方式がずれると「違う」と誤認する。
- 画素レベルの完全一致を求める前に、まず**丸め（開始位置・座標→画素）**を疑う。小数第数位で丸めているかを揃える。
- ハッシュを使うなら、「何に対する（生画素か int32 キャストか）」「どのハッシュか（SHA-256 全体か短縮か）」を
  実験記録に明記する。短縮表示は**表示だけ**の問題で中身は同じこともある。
- greedy 復号のモデルは同一入力→同一出力なので、**入力が1pxでもずれると判断が変わり得る**。入力の再現性は判断の再現性の前提。
