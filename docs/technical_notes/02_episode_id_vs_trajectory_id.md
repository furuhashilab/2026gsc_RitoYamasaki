# 技術ノート 02: episode_id と trajectory_id の取り違え

> 後輩が同じ問題に遭遇したときの参考用。R2R の GT 行動を再生する際にハマりやすい取り違え。
> 一次ログは研究室Mac上にあり、本文書更新環境では再照合していない。ここでは現象・原因・対処を整理する。

## 現象

R2R（Room-to-Room）系のデータで **GT（正解経路）行動を再生**するとき、エピソードを指す ID を取り違えると、
**意図したエピソードと別の経路を再生**してしまう。本研究では ep85・ep280 の GT 再生を扱う中で、この取り違えに注意した。

## なぜ起きるか

R2R には似て非なる2種類の ID があり、意味が異なる。

- **`episode_id`**: 評価データセット内でエピソード（＝「あるシーン上で、ある指示に従う1タスク」）を識別する ID。
- **`trajectory_id`（path_id / instruction 由来の ID）**: 元の R2R パス（経路）や指示の ID。

1つの経路（trajectory）に複数の言い換え指示が紐づくなど、両者は **1対1に対応しない**。
`episode_id` のつもりで `trajectory_id`（またはその逆）を使うと、GT 経路・開始 pose・ゴールが**別物**になり、
「再生したら終点が合わない／測地距離が記録値と違う」という形で表面化する。

## 本研究での対処・確認

- 対象を **ep85・ep280** と明示し、GT 行動を再生した結果、
  - **正解経路の終点への一致**、
  - **開始位置→ゴールの測地距離が記録値と一致**、
  を確認した（報告）。これらは「正しいエピソードを正しく参照できている」ことの検算になる。
- つまり、終点一致・測地距離一致を**取り違え検出のチェックとして使う**のが有効。

## 後輩への教訓

- GT 再生では、**どの ID でエピソードを引いているか**をコード上で明示し、`episode_id` と `trajectory_id`（path_id）を混同しない。
- 再生後は必ず **終点一致・測地距離** を記録値と突き合わせる。ずれたら、まず ID の取り違えを疑う。
- ログに「参照した ID の種類・値」と「検算（終点・測地距離）」を残すと、後からの追跡が容易になる。
